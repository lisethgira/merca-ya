1. Introducción
MercaYa es una aplicación web progresiva (PWA) de comercio electrónico tipo marketplace, desarrollada con React + Vite PWA y Tailwind CSS en el frontend, Node.js + Express en el backend y MySQL alojado en Clever Cloud. En ella múltiples vendedores publican productos de distintas categorías y los clientes pueden buscarlos, comprarlos, pagarlos y calificarlos desde cualquier dispositivo, bajo la supervisión de un administrador.
Este documento especifica los requisitos funcionales y no funcionales del sistema, siguiendo los lineamientos de la norma ISO/IEC/IEEE 29148:2018 y el modelo de calidad de producto ISO/IEC 25010:2023. Cada requisito tiene un identificador único, una descripción verificable, el rol involucrado y su prioridad, para facilitar la trazabilidad con las historias de usuario y las pruebas.

2. Requisitos funcionales
Los requisitos funcionales describen los servicios que el sistema debe proporcionar y cómo debe reaccionar ante entradas y situaciones particulares (Sommerville, 2016). Se identifican con el prefijo RF, se agrupan por módulo y se priorizan como Alta, Media o Baja según su valor para el producto mínimo viable (MVP).

3. Requisitos no funcionales
Los requisitos no funcionales establecen restricciones y atributos de calidad del sistema. Se clasifican según las características del modelo de calidad de producto ISO/IEC 25010:2023 (eficiencia de desempeño, seguridad, usabilidad, compatibilidad, fiabilidad, mantenibilidad y portabilidad) e incorporan exigencias legales colombianas. Cada requisito incluye un criterio verificable para su aceptación.
ID
Categoría
Descripción
Criterio de verificación
RNF01
Rendimiento
La PWA debe obtener una puntuación ≥ 90 en Lighthouse (Performance) en móvil y un LCP inferior a 2,5 s en red 4G.
Auditoría Lighthouse en cada release
RNF02
Rendimiento
Los endpoints de consulta del catálogo deben responder en menos de 500 ms en el percentil 95 con 100 usuarios concurrentes.
Pruebas de carga (k6 / Artillery)
RNF03
Portabilidad (PWA)
La aplicación debe cumplir los criterios de instalabilidad: manifest.webmanifest con nombre, colores e íconos 192 y 512 px (incluye maskable), service worker generado con vite-plugin-pwa (Workbox) y servicio por HTTPS.
Chrome DevTools > Application
RNF04
Disponibilidad offline
Estrategias de caché: CacheFirst para recursos estáticos, StaleWhileRevalidate para imágenes y NetworkFirst para la API del catálogo; página de respaldo /offline.
Prueba en modo avión
RNF05
Seguridad
Las contraseñas se almacenan con bcrypt (mínimo 10 rondas) y deben tener al menos 8 caracteres, una mayúscula, un número y un símbolo.
Revisión de código y pruebas unitarias
RNF06
Seguridad
Token de acceso JWT con vigencia de 15 minutos y token de refresco de 7 días en cookie httpOnly, Secure y SameSite.
Pruebas de integración
RNF07
Seguridad
El backend aplica los controles del OWASP Top 10: helmet, CORS restringido al dominio del frontend, express-rate-limit en login (5 intentos/15 min), validación de entradas (zod o express-validator) y consultas parametrizadas con mysql2 para evitar inyección SQL.
Checklist OWASP / escaneo ZAP
RNF08
Seguridad
Toda la comunicación se realiza sobre HTTPS/TLS (certificados de Vercel y Clever Cloud).
Verificación de certificados
RNF09
Legal
El tratamiento de datos personales cumple la Ley 1581 de 2012 (Habeas Data): política visible, consentimiento explícito en el registro y opción de eliminación de la cuenta.
Revisión legal / checklist
RNF10
Legal / Seguridad
La aplicación no almacena datos de tarjetas; el pago se delega a la pasarela certificada PCI DSS y solo se guardan referencias y estados.
Revisión del modelo de datos
RNF11
Usabilidad
Diseño mobile-first y responsive entre 320 px y 1920 px usando los breakpoints de Tailwind CSS; una compra debe completarse en máximo 5 pasos desde el carrito.
Pruebas de usabilidad con 5 usuarios
RNF12
Accesibilidad
Cumplimiento del nivel AA de WCAG 2.1: contraste mínimo 4,5:1, navegación por teclado, textos alternativos y etiquetas en formularios.
Lighthouse Accessibility ≥ 90 / axe
RNF13
Compatibilidad
Funciona en las dos últimas versiones de Chrome, Edge, Firefox y Safari; Android 9+ e iOS 16.4+ (las notificaciones push en iOS requieren la PWA instalada).
Pruebas cruzadas en dispositivos
RNF14
Disponibilidad
Disponibilidad mínima del 99 % mensual en frontend (Vercel) y backend/base de datos (Clever Cloud).
Monitoreo (UptimeRobot)
RNF15
Integridad
El checkout se ejecuta en una transacción InnoDB; el stock se descuenta con UPDATE condicional (stock >= cantidad) para evitar sobreventa.
Pruebas de concurrencia
RNF16
Recuperabilidad
Se conservan copias de seguridad automáticas de la base de datos según el plan de Clever Cloud y un respaldo manual semanal (mysqldump).
Restauración de prueba trimestral
RNF17
Eficiencia de recursos
El backend usa un pool de conexiones mysql2 con connectionLimit ajustado al máximo de conexiones del plan de Clever Cloud (los planes gratuitos/pequeños tienen límites bajos).
Revisión de configuración
RNF18
Mantenibilidad
Backend organizado por capas o arquitectura hexagonal (rutas → controladores → casos de uso → repositorios), ESLint + Prettier, Git con ramas y commits convencionales.
Revisión de pull requests
RNF19
Mantenibilidad
Cobertura mínima de pruebas del 70 % en servicios y casos de uso (Vitest/Jest + Supertest).
Reporte de cobertura en CI
RNF20
Mantenibilidad
La API REST se documenta con OpenAPI/Swagger y versiona sus rutas (/api/v1).
Swagger UI publicado
RNF21
Escalabilidad
Las imágenes se guardan en un servicio externo (Cloudinary o Cellar S3 de Clever Cloud), no en la base de datos; todos los listados son paginados.
Revisión de arquitectura
RNF22
Localización
Interfaz en español, moneda en pesos colombianos con formato es-CO (Intl.NumberFormat) y zona horaria America/Bogota.
Pruebas funcionales
RNF23
Observabilidad
Registro de peticiones y errores (morgan/winston) con manejo centralizado de excepciones y respuestas de error uniformes.
Revisión de logs
4. Conclusiones
La especificación de 42 requisitos funcionales, organizados en cinco módulos, delimita con precisión las responsabilidades de los roles administrador, vendedor y cliente, y cubre el ciclo completo del marketplace: registro, aprobación de tiendas, publicación, catálogo, carrito, pago, seguimiento, reseñas y notificaciones.
Los 23 requisitos no funcionales, clasificados según ISO/IEC 25010:2023 y acompañados de un criterio de verificación, convierten atributos de calidad como rendimiento, seguridad, accesibilidad y funcionamiento offline en metas medibles, e incorporan obligaciones legales colombianas como la Ley 1581 de 2012.
La priorización Alta, Media y Baja permite definir el producto mínimo viable y sirve de base para derivar las historias de usuario, el modelo de datos y los casos de prueba.
