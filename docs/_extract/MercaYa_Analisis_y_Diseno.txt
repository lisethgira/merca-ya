1. Introducción
MercaYa es una aplicación web progresiva (PWA) de comercio electrónico tipo marketplace, en la que múltiples vendedores publican productos de distintas categorías y los clientes pueden buscarlos, comprarlos, pagarlos y calificarlos desde cualquier dispositivo, con la posibilidad de instalar la aplicación en la pantalla de inicio y consultarla aun con conectividad limitada. La plataforma es supervisada por un administrador que aprueba tiendas, modera publicaciones y atiende reportes.
El presente documento reúne los artefactos de análisis y diseño del proyecto: la identidad visual, la especificación de requisitos funcionales y no funcionales, organizada según los lineamientos de la norma ISO/IEC/IEEE 29148:2018 y el modelo de calidad ISO/IEC 25010:2023; las historias de usuario con criterios de aceptación bajo el enfoque propuesto por Cohn (2004); el modelo entidad-relación y el script SQL de creación de la base de datos relacional en MySQL 8 alojada en Clever Cloud.
1.1 Objetivo general
Desarrollar una PWA de compra y venta de productos varios que conecte vendedores locales con clientes, garantizando una experiencia rápida, segura, instalable y disponible sin conexión.
1.2 Objetivos específicos
Especificar los requisitos funcionales y no funcionales para los roles administrador, vendedor y cliente.
Traducir los requisitos en historias de usuario priorizadas y estimadas para un desarrollo ágil (Scrum).
Diseñar un modelo de datos relacional normalizado que soporte pedidos multivendedor, pagos, reseñas y notificaciones.
Implementar la base de datos en MySQL sobre Clever Cloud con integridad referencial, índices y datos iniciales.
1.3 Alcance
El alcance comprende el registro y autenticación con roles, la gestión de tiendas y productos, el catálogo con búsqueda y filtros, el carrito, el checkout con pasarela de pagos colombiana o contraentrega, el seguimiento de pedidos por ítem, las reseñas, las preguntas, los reportes, las notificaciones internas y push, y las capacidades PWA (instalación y modo sin conexión). Quedan fuera del alcance inicial la logística propia de envíos, la facturación electrónica ante la DIAN y el chat en tiempo real, que se proponen para versiones posteriores.

El logo de MercaYa combina una bolsa de compras, símbolo universal del comercio, con un rayo que expresa la inmediatez de la marca («¡ya!»): comprar y vender de forma rápida y sencilla. 4. Requisitos no funcionales
Los requisitos no funcionales establecen restricciones y atributos de calidad del sistema. Se clasifican según las características del modelo de calidad de producto ISO/IEC 25010:2023 (eficiencia de desempeño, seguridad, usabilidad, compatibilidad, fiabilidad, mantenibilidad y portabilidad) e incorporan exigencias legales colombianas. Cada requisito incluye un criterio verificable para su aceptación.
ID
Categoría
Descripción
Criterio de verificación
RNF01
Rendimiento
La PWA debe obtener una puntuación ≥ 90 en Lighthouse (Performance) en móvil y un LCP inferior a 2,5 s en red 4G.
Auditoría Lighthouse en cada release
RNF02
Rendimiento
Los endpoints de consulta del catálogo deben responder en menos de 500 ms en el percentil 95 con 100 usuarios concurrentes.
Pruebas de carga (k6 / Artillery)
RNF03
Portabilidad (PWA)
La aplicación debe cumplir los criterios de instalabilidad: manifest.webmanifest con nombre, colores e íconos 192 y 512 px (incluye maskable), service worker generado con vite-plugin-pwa (Workbox) y servicio por HTTPS.
Chrome DevTools > Application
RNF04
Disponibilidad offline
Estrategias de caché: CacheFirst para recursos estáticos, StaleWhileRevalidate para imágenes y NetworkFirst para la API del catálogo; página de respaldo /offline.
Prueba en modo avión
RNF05
Seguridad
Las contraseñas se almacenan con bcrypt (mínimo 10 rondas) y deben tener al menos 8 caracteres, una mayúscula, un número y un símbolo.
Revisión de código y pruebas unitarias
RNF06
Seguridad
Token de acceso JWT con vigencia de 15 minutos y token de refresco de 7 días en cookie httpOnly, Secure y SameSite.
Pruebas de integración
RNF07
Seguridad
El backend aplica los controles del OWASP Top 10: helmet, CORS restringido al dominio del frontend, express-rate-limit en login (5 intentos/15 min), validación de entradas (zod o express-validator) y consultas parametrizadas con mysql2 para evitar inyección SQL.
Checklist OWASP / escaneo ZAP
RNF08
Seguridad
Toda la comunicación se realiza sobre HTTPS/TLS (certificados de Vercel y Clever Cloud).
Verificación de certificados
RNF09
Legal
El tratamiento de datos personales cumple la Ley 1581 de 2012 (Habeas Data): política visible, consentimiento explícito en el registro y opción de eliminación de la cuenta.
Revisión legal / checklist
RNF10
Legal / Seguridad
La aplicación no almacena datos de tarjetas; el pago se delega a la pasarela certificada PCI DSS y solo se guardan referencias y estados.

RNF11
Usabilidad
Diseño mobile-first y responsive entre 320 px y 1920 px usando los breakpoints de Tailwind CSS; una compra debe completarse en máximo 5 pasos desde el carrito.

Accesibilidad
Cumplimiento del nivel AA de WCAG 2.1: contraste mínimo 4,5:1, navegación por teclado, textos alternativos y etiquetas en formularios.
Lighthouse Accessibility ≥ 90 / axe
RNF13
Compatibilidad

Disponibilidad
Disponibilidad mínima del 99 % mensual en frontend (Vercel) y backend/base de datos (Clever Cloud).

5.2 Detalle de las historias de usuario
HU01 · Registro de cliente
Historia
Como visitante, quiero registrarme con mi correo y una contraseña, para poder comprar productos y guardar mi información.
Criterios de aceptación
CA1. Dado que ingreso datos válidos y acepto la política de datos, cuando envío el formulario, entonces se crea mi cuenta con rol cliente y quedo autenticado.
CA2. Si el correo ya existe, se muestra «El correo ya está registrado».
CA3. La contraseña debe cumplir la política de seguridad (RNF05).
Prioridad / Estimación
Must · 3 puntos · Requisitos relacionados: RF01
HU02 · Inicio de sesión
Historia
Como usuario registrado, quiero iniciar sesión con correo y contraseña, para acceder a las funciones de mi rol.
Criterios de aceptación
CA1. Con credenciales válidas se me redirige a mi panel (admin, vendedor o catálogo).
CA2. Con credenciales inválidas se muestra un mensaje genérico sin revelar cuál dato falló.
CA3. Tras 5 intentos fallidos en 15 minutos se bloquea temporalmente el intento.
Prioridad / Estimación
Must · 3 puntos · Requisitos relacionados: RF03, RF08
HU03 · Recuperar contraseña
Historia
Como usuario registrado, quiero restablecer mi contraseña desde mi correo, para recuperar el acceso si la olvido.
Criterios de aceptación
CA1. Recibo un enlace con vigencia de 30 minutos.
CA2. El enlace solo puede usarse una vez.
CA3. Al cambiarla se cierran las sesiones activas.
Prioridad / Estimación
Should · 3 puntos · Requisitos relacionados: RF05
HU04 · Gestionar direcciones
Historia
Como cliente, quiero guardar varias direcciones de envío, para no digitarlas en cada compra.
Criterios de aceptación
CA1. Puedo crear, editar y eliminar direcciones.
CA2. Solo una dirección puede ser principal.
CA3. La dirección principal se selecciona por defecto en el checkout.
Prioridad / Estimación
Must · 2 puntos · Requisitos relacionados: RF07
HU05 · Abrir mi tienda
Historia
Como usuario, quiero solicitar convertirme en vendedor creando mi tienda, para publicar y vender mis productos.

6. Modelo entidad-relación
El modelo de datos se diseñó a partir de los requisitos funcionales, identificando entidades, atributos, claves y cardinalidades (Elmasri & Navathe, 2016). Está normalizado hasta la tercera forma normal (3FN), con desnormalizaciones controladas y justificadas: la copia de la dirección y del nombre del producto en pedidos y detalle_pedido conserva el histórico aunque los datos originales cambien, y el campo calificacion_promedio evita recalcular promedios en cada consulta del catálogo.
6.1 Decisiones de diseño relevantes
Pedidos multivendedor: un pedido puede incluir productos de varias tiendas; por eso el estado de envío y la guía se manejan por ítem en detalle_pedido, y cada vendedor solo gestiona sus ítems.
Vendedor como tienda: la tienda es una entidad 1:1 con el usuario vendedor, con flujo de aprobación (pendiente, aprobada, rechazada, suspendida) auditado por el administrador.
Categorías jerárquicas: autorrelación padre_id que permite categorías y subcategorías sin tablas adicionales.
Reseñas verificadas: cada reseña se vincula 1:1 con un ítem de pedido, lo que garantiza que solo opine quien compró y evita duplicados.
Relaciones N:M: favoritos (usuarios-productos) y carrito_items (carritos-productos) se resuelven con entidades asociativas.
PWA: suscripciones_push almacena las claves Web Push de cada dispositivo y notificaciones sirve como bandeja persistente.

6.3 Diagrama entidad-relación
El diagrama utiliza la notación de pata de gallo (crow's foot): dos barras indican «uno y solo uno», el círculo con pata de gallo indica «cero o muchos» y el círculo con barra «cero o uno». Las tablas se agrupan en tres módulos: usuarios y acceso (índigo), catálogo e interacción (violeta) y compras (naranja). PK = clave primaria; FK = clave foránea.

7. Script de la base de datos (MySQL · Clever Cloud)
El script mercaya_db.sql crea las 18 tablas con motor InnoDB y juego de caracteres utf8mb4 (soporte de tildes, ñ y emojis), claves primarias y foráneas con reglas ON DELETE/ON UPDATE, restricciones CHECK (MySQL 8.0.16 o superior), índices de búsqueda (incluido un índice FULLTEXT), dos vistas de apoyo (v_catalogo y v_ventas_por_tienda) y datos iniciales. El script fue ejecutado y validado sin errores en MySQL 8.0.
7.1 Pasos para ejecutarlo en Clever Cloud
En la consola de Clever Cloud, crear el add-on MySQL y seleccionar el plan y la región.
Copiar las credenciales de la pestaña de información del add-on (host, puerto, base de datos, usuario y contraseña). La base de datos ya viene creada, por lo que el script no incluye CREATE DATABASE.
Conectarse con phpMyAdmin (enlace del add-on), MySQL Workbench o la terminal: mysql -h HOST -P PUERTO -u USUARIO -p BASE < mercaya_db.sql
Verificar con SHOW TABLES; que existan las 18 tablas y 2 vistas.
Usuarios de prueba (contraseña MercaYa2026*): admin@mercaya.com, vendedor@mercaya.com y cliente@mercaya.com. Cambiarla antes de producción.
7.2 Conexión desde Express
Clever Cloud expone las variables de entorno MYSQL_ADDON_HOST, MYSQL_ADDON_PORT, MYSQL_ADDON_DB, MYSQL_ADDON_USER y MYSQL_ADDON_PASSWORD cuando el add-on está vinculado a la aplicación Node.js. Se recomienda un pool de conexiones con límite bajo, acorde con el plan:
// src/infrastructure/db/pool.js
import mysql from 'mysql2/promise';
export const pool = mysql.createPool({
host: process.env.MYSQL_ADDON_HOST,
port: Number(process.env.MYSQL_ADDON_PORT),
database: process.env.MYSQL_ADDON_DB,
user: process.env.MYSQL_ADDON_USER,
password: process.env.MYSQL_ADDON_PASSWORD,
waitForConnections: true,
connectionLimit: 4,      // ajustar al máximo de conexiones del plan
charset: 'utf8mb4',
timezone: '-05:00'       // America/Bogota
});

-- CREATE DATABASE IF NOT EXISTS mercaya CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- ---------------------------------------------------------------------
-- 1. ROLES (administrador, vendedor, cliente)
-- ---------------------------------------------------------------------
CREATE TABLE roles (
id            TINYINT UNSIGNED NOT NULL AUTO_INCREMENT,
nombre        VARCHAR(30)  NOT NULL,
descripcion   VARCHAR(150) NULL,
PRIMARY KEY (id),
UNIQUE KEY uq_roles_nombre (nombre)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
-- ---------------------------------------------------------------------
-- 2. USUARIOS
-- ---------------------------------------------------------------------
CREATE TABLE usuarios (
id                 INT UNSIGNED NOT NULL AUTO_INCREMENT,
rol_id             TINYINT UNSIGNED NOT NULL,
nombres            VARCHAR(80)  NOT NULL,
apellidos          VARCHAR(80)  NOT NULL,
tipo_documento     ENUM('CC','CE','TI','PASAPORTE','NIT') NULL,
numero_documento   VARCHAR(20)  NULL,
email              VARCHAR(120) NOT NULL,
password_hash      VARCHAR(255) NOT NULL,          -- bcrypt
telefono           VARCHAR(20)  NULL,
avatar_url         VARCHAR(255) NULL,
email_verificado   TINYINT(1)   NOT NULL DEFAULT 0,
estado             ENUM('activo','inactivo','bloqueado') NOT NULL DEFAULT 'activo',
ultimo_acceso      DATETIME     NULL,
created_at         DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at         DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
PRIMARY KEY (id),
UNIQUE KEY uq_usuarios_email (email),
UNIQUE KEY uq_usuarios_documento (tipo_documento, numero_documento),
KEY idx_usuarios_rol (rol_id),
CONSTRAINT fk_usuarios_rol FOREIGN KEY (rol_id) REFERENCES roles (id)
ON UPDATE CASCADE ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
-- ---------------------------------------------------------------------
-- 3. DIRECCIONES (un usuario puede tener varias direcciones de envío)
-- ---------------------------------------------------------------------
CREATE TABLE direcciones (
id             INT UNSIGNED NOT NULL AUTO_INCREMENT,
usuario_id     INT UNSIGNED NOT NULL,

municipio      VARCHAR(60)  NOT NULL,

direccion      VARCHAR(150) NOT NULL,
referencia     VARCHAR(150) NULL,

created_at     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
PRIMARY KEY (id),
KEY idx_direcciones_usuario (usuario_id),
CONSTRAINT fk_direcciones_usuario FOREIGN KEY (usuario_id) REFERENCES usuarios (id)
ON UPDATE CASCADE ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
-- ---------------------------------------------------------------------
-- 4. TIENDAS (perfil comercial del vendedor, 1 a 1 con usuario)
-- ---------------------------------------------------------------------
CREATE TABLE tiendas (
id                     INT UNSIGNED NOT NULL AUTO_INCREMENT,
usuario_id             INT UNSIGNED NOT NULL,
nombre                 VARCHAR(100) NOT NULL,
slug                   VARCHAR(120) NOT NULL,
descripcion            TEXT         NULL,
logo_url               VARCHAR(255) NULL,
telefono_contacto      VARCHAR(20)  NULL,
municipio              VARCHAR(60)  NULL,
estado                 ENUM('pendiente','aprobada','rechazada','suspendida') NOT NULL DEFAULT 'pendiente',
motivo_estado          VARCHAR(255) NULL,
calificacion_promedio  DECIMAL(3,2) NOT NULL DEFAULT 0.00,
aprobada_por           INT UNSIGNED NULL,             -- administrador que aprobó
aprobada_en            DATETIME     NULL,
created_at             DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
updated_at             DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
PRIMARY KEY (id),
UNIQUE KEY uq_tiendas_usuario (usuario_id),
UNIQUE KEY uq_tiendas_slug (slug),
KEY idx_tiendas_estado (estado),
CONSTRAINT fk_tiendas_usuario FOREIGN KEY (usuario_id) REFERENCES usuarios (id)
ON UPDATE CASCADE ON DELETE CASCADE,
CONSTRAINT fk_tiendas_admin FOREIGN KEY (aprobada_por) REFERENCES usuarios (id)
ON UPDATE CASCADE ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
-- ---------------------------------------------------------------------
-- 5. CATEGORIAS (jerárquicas: categoría / subcategoría)
-- ---------------------------------------------------------------------
CREATE TABLE categorias (
id           INT UNSIGNED NOT NULL AUTO_INCREMENT,
padre_id     INT UNSIGNED NULL,
nombre       VARCHAR(80)  NOT NULL,
slug         VARCHAR(100) NOT NULL,
descripcion  VARCHAR(255) NULL,
icono        VARCHAR(60)  NULL,

created_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
PRIMARY KEY (id),
UNIQUE KEY uq_categorias_slug (slug),
KEY idx_categorias_padre (padre_id),
CONSTRAINT fk_categorias_padre FOREIGN KEY (padre_id) REFERENCES categorias (id)
ON UPDATE CASCADE ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
-- ---------------------------------------------------------------------
-- 6. PRODUCTOS
-- ---------------------------------------------------------------------
CREATE TABLE productos (
id              INT UNSIGNED NOT NULL AUTO_INCREMENT,
tienda_id       INT UNSIGNED NOT NULL,

slug            VARCHAR(170) NOT NULL,
descripcion     TEXT         NULL,
precio          DECIMAL(12,2) NOT NULL,

stock           INT UNSIGNED NOT NULL DEFAULT 0,
sku             VARCHAR(50)  NULL,
condicion       ENUM('nuevo','usado','reacondicionado') NOT NULL DEFAULT 'nuevo',
estado          ENUM('borrador','pendiente','publicado','pausado','rechazado') NOT NULL DEFAULT 'pendiente',
motivo_rechazo  VARCHAR(255) NULL,
vistas          INT UNSIGNED NOT NULL DEFAULT 0,

CREATE OR REPLACE VIEW v_catalogo AS
SELECT p.id, p.nombre, p.slug, p.precio, p.precio_oferta,
COALESCE(p.precio_oferta, p.precio) AS precio_final,
p.stock, p.condicion, p.calificacion_promedio,
c.id AS categoria_id, c.nombre AS categoria,
t.id AS tienda_id, t.nombre AS tienda, t.municipio,
(SELECT i.url FROM producto_imagenes i
WHERE i.producto_id = p.id
ORDER BY i.es_principal DESC, i.orden ASC LIMIT 1) AS imagen,
p.created_at
FROM productos p
JOIN categorias c ON c.id = p.categoria_id
JOIN tiendas    t ON t.id = p.tienda_id
WHERE p.estado = 'publicado' AND t.estado = 'aprobada' AND c.activa = 1;
CREATE OR REPLACE VIEW v_ventas_por_tienda AS
SELECT t.id AS tienda_id, t.nombre AS tienda,
COUNT(DISTINCT d.pedido_id)  AS pedidos,
COALESCE(SUM(d.cantidad), 0) AS unidades_vendidas,
COALESCE(SUM(d.subtotal), 0) AS total_vendido
FROM tiendas t
LEFT JOIN detalle_pedido d ON d.tienda_id = t.id AND d.estado_item <> 'cancelado'
GROUP BY t.id, t.nombre;

8. Conclusiones
La especificación de 42 requisitos funcionales organizados por módulos y 23 requisitos no funcionales verificables ofrece una base clara y medible para el desarrollo de MercaYa, y permite distinguir con precisión las responsabilidades de los roles administrador, vendedor y cliente.
Las 28 historias de usuario, priorizadas con MoSCoW y estimadas en 103 puntos, facilitan la planificación de sprints: las historias «Must» conforman el producto mínimo viable (registro, tiendas, publicación, catálogo, carrito, pago, seguimiento e instalación PWA), mientras que las «Should» y «Could» enriquecen versiones posteriores.
El modelo entidad-relación de 18 entidades en tercera forma normal soporta el escenario multivendedor, conserva el histórico de las compras y garantiza la integridad mediante claves foráneas, restricciones CHECK y transacciones InnoDB. Su implementación en MySQL sobre Clever Cloud, junto con React + Vite PWA y Express, conforma una arquitectura moderna, desplegable en la nube y alineada con las buenas prácticas de seguridad del OWASP Top 10 y la normativa colombiana de protección de datos.
